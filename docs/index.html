Speech QC: is this recording good enough to pay for?

Contributors read a sentence aloud on their phone. Before we pay for it and ship it to a buyer, this check decides: accept or re-record, with a reason the contributor sees. Try it with your own voice in English or Russian, including the mistakes contributors make.

How it works

Two layers. Cheap checks run on the phone, so a bad take is re-recorded on the spot and never uploaded. The server re-checks everything, because a phone can be tampered with, then runs speech recognition. Steps light up as your recording goes through.

Contributor's phone (this browser)
Record16 kHz mono WAV
Phone checkslength, silence, clipping, loudness, noise
Uploadaudio + the prompt shown
Server · Supabase edge function qc-check
Re-check signalsame checks; never trust the phone
Store recordingSupabase Storage, private bucket
Speech recognitionWhisper: language + words
Decidelanguage matches, text error ≤ limit
Log the decisionPostgres qc.checks (own schema, not exposed): feeds the buyer report, the 10% batch rule and threshold tuning

At scale the same function sits behind a queue; the few borderline recordings (target ≤5% of volume) go to human review instead of an automatic verdict, and accepted recordings are packed into buyer batches that must stay under the buyer's 10% rejection rule.

What this does not prove yet

  • The measured numbers come from planted defects on real recordings, so labels are known. Real buyer decisions are the next test.
  • FLEURS is read in quiet rooms. Car noise, phone microphones and spontaneous speech will be harder.
  • This live server uses Whisper large-v3 (hosted) instead of Whisper small used in the measurement, and English and Russian reuse the Spanish text limit. Both are untested against the targets.
